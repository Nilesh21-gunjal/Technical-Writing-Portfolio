Developer documentation · Public-safe sample

Device Operations API

A developer-facing documentation set for a fictional connected-device API, built to show how onboarding, concepts, task guidance, reference, examples, validation, and support fit together.

Start with the quickstart Open API reference

Challenge and audience

Generated API reference is useful, but it does not by itself help a new developer understand a resource model, make a first request, recover from an error, or evaluate integration behavior. This sample pairs an OpenAPI 3.0.3 contract with human-written content organized around those developer needs.

Role and scope

This sample demonstrates information architecture, API reference, task guidance, examples, and validation for developers and integration teams connecting a client application to a device operations service.

What I built

  • A validated OpenAPI contract with 7 paths and 10 operations across authentication, devices, telemetry, alerts, and usage.
  • Task-based onboarding, concepts, guides, a tutorial, troubleshooting, glossary, FAQ, changelog, and a proposed versioning and deprecation policy.
  • Copy-ready cURL, Python, and JavaScript examples, a Postman collection, and a local Prism mock that returns documented examples.
  • Public-safe content that uses fictional identifiers, URLs, payloads, and credentials rather than employer or customer information.

Portfolio outcome

The result is a reviewable and runnable documentation portal that connects human-written guidance with a validated API contract and repeatable quality checks. It demonstrates developer experience, information architecture, API documentation, and Docs-as-Code maintenance without claiming production adoption or performance.

Review path

Use this path to evaluate the sample quickly:

  1. Run the Quickstart to see the first-request path and safe local mock boundary.
  2. Read Errors and troubleshooting to see status, error-code, cause, and recovery guidance.
  3. Open the interactive API reference to inspect the contract, examples, schemas, and endpoint descriptions.
  4. Review the documentation decisions for the reasoning behind content structure, pagination, errors, versioning, and validation.

Documentation decisions

AudienceDevelopers and integration teams who need to connect a client application to a device operations service.
Information architectureConcepts explain the model; task guides support a developer goal; generated reference provides exact contract details; support content explains recovery.
Local testingPrism returns documented examples so the cURL, Python, JavaScript, and Postman samples can be exercised without a live API.
Public-safe approachGeneric resource names, example values, placeholder credentials, and fictional URLs keep the sample useful without reproducing employer-owned information.

Quality and maintenance

  • OpenAPI schema validation with Redocly and Spectral rules.
  • Contract tests, code-example checks, and a Postman collection tested against the local mock.
  • Strict static-site builds, link checks, prose linting, and HTML accessibility essentials.
  • A source-controlled documentation workflow that can be reviewed through Git and GitHub Actions.
Public-safe note: This is an independent demonstration. The local mock does not persist data, validate credentials, or simulate production behavior. The sample contains no internal URLs, customer data, production identifiers, proprietary architecture, or employer-owned source content.
